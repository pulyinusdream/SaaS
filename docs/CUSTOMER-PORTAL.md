# Customer user side

User explicitly confirmed customers request service and see only their own requests while Admin manages the business. Plans/Usage is paused. Implement inline in existing Flask/Jinja/SQLite, mint framed sheet, IBM Plex Sans and SVG system; no new dependency, deployment, SMTP purchase, external AI or billing. Existing owner/dispatcher staff remain tenant-scoped Admin; this does not introduce a global super-admin.

Approach: separate customer account kind and customer_accounts profile bound to one business, never dispatcher membership. Existing users default staff. Customer registration starts from the business public link /customer/signup/<public_id>, creates an account and contact profile without any workspace or membership. /customer/login reuses the secure password/session implementation but accepts only customer accounts; /login accepts only staff. Signed-in wrong-portal entry shows an explicit sign-out/switch boundary. Existing /signup continues staff/business registration. Customer invite acceptance and every Admin workspace route are denied on server even if an erroneous membership exists. Existing credentials and public URLs remain valid. Staff see a read-only guest-form preview; signed-in customers use only their own business's authenticated form; anonymous guest submission remains usable.

GET /customer is My requests, filtered only by signed-in customer ID plus profile's business ID,25/page, current status counts/filter and explicit empty/error states. Detail /customer/requests/<lead_id> uses explicit safe fields; shows submitted service/location/contact/message, current status and saved appointment dates/state in business timezone. No internal notes, activity actor strings, private follow-up actions/outcomes, staff emails/IDs or cancellation reasons are exposed. Customer cannot edit status, schedule/cancel appointments, access reports/team/settings/other customer requests or claim guest records by email. Admin continues processing ordinary lead rows and customer sees changes on refresh.

Get Started /customer/get-started saves optional phone and required default service location (200 characters) to personal profile, with version checks and completed_at. Name/email are current account values, editable only through existing safe account settings. Contact defaults prefill requests; each request can use another address/phone without overwriting the profile. No completion is invented; required setup is contact defaults, then a first portal request. Account settings/session controls and email verification/recovery apply to customers too. Strict email gating remains in force.

Customer form /customer/form resolves the business from authenticated profile, validates current service catalogue/contact/address/message with existing lead validation, and sets name/email/customer_user_id/source='customer_portal' on server. It uses a one-hour signed per-form nonce bound to customer/business and an existing unique submission_key; replay redirects to the same owned request instead of duplicating it. All customer mutations BEGIN IMMEDIATE then refresh exact active session/account kind/profile/business, preserving CSRF/origin guards and rejecting revocation or changed kind after identity load. Stored default contact data is escaped and versioned. Public business identity controls routing only at registration, never a submitted company/user ID.

Migration: users.account_kind default staff CHECK staff/customer; leads.customer_user_id optional FK users; new customer_accounts keyed to user, workspace FK, phone/location/version/completed_at. Add a customer/tenant/created index after migration. No existing row is reclassified or retrospectively attached. New portal inquiries count toward business's existing inbound-inquiry setup evidence.

Navigation: customer shell with Customer account label, My requests, Get Started, Customer Form and Account settings; mint shell shared without staff links. Admin sidebar loses Get Started and Customer Form, retains Lead inbox/Calendar/Team/Reports/Business settings/workspaces/account. Business setup remains accessible from Business Settings with that name; remove onboarding and customer-form capture promotions from Admin inbox while retaining its connected marketing website controls. Legacy /setup route remains owner-only Business setup; its checklist/public link stays accessible for administration. Public forms and marketing remain guest-compatible.

Sample: explicit local-only create_sample_customer.py command, never automatic launch seeding or static/default password. Create an isolated Sample Customer Workspace owned by the chosen existing staff owner, one customer account sample.customer@kjancy.test, generated random password hashed in DB, saved default profile and one clearly fictional portal request. No membership is granted to customer. Refuse email/name collisions and production SMTP/HTTPS mode; don't overwrite credentials on rerun. Save one private credential file outside published app/source ZIP. Existing rows must remain byte-for-byte unchanged; authorized sample records are additive. Sample remains visibly labelled as sample data.
