# Simple Customer and Admin UI Implementation Plan

> Execute inline using executing-plans/TDD. User requested both UIs be simpler and easier to understand, and permits routine design decisions without additional approval. One independent read-only review at the end. No Git repository; work/saas/pre-simple-ui-source.zip preserves baseline.

**Goal:** Make everyday tasks obvious and reduce competing controls while retaining all existing business/security behavior.
**Architecture:** Existing Flask/Jinja/native forms and disclosure elements; one shared usability stylesheet, no new dependency or schema. Keep mint/IBM Plex Sans framed-sheet identity. Customer-owned request APIs and staff guards unchanged.

## Design

Use task-first navigation: Customer My requests/New request/Contact details/My account, Admin daily work separate from business management. Plain labels, visible sign-out, readable type, consistent 44px controls and one clear primary action. Remove decorative sidebar/footer copy. Replace dense request status tabs and work-view strips with labelled GET filters. Put connected-site/timezone tools below the work list. Keep Add a lead for staff recording received inquiries.

Customer contact defaults are a simple form; new requests use clear service/contact/message groups, and tracking explains the current status without invented linear progress. Account Profile is open initially; Password and Signed-in browsers use native expandable sections. Validation opens the correct section on the server. Existing #password/#sessions links and error anchors open ancestor details in progressive JavaScript. Controls remain usable without JavaScript via native summaries.

Admin request detail keeps contact and status/notes readily visible; follow-up editing/activity become expandable, with follow-up errors/pending work expanded. App-wide spacing/type/navigation improve secondary Calendar/Team/Reports/Business settings too. Preserve dangerous-action explanations, local-preview honesty, disabled/stale states, field names, CSRF/version tokens, POST destinations, pagination and filter semantics. No credential/live-data changes, new permissions or external services.

Alternatives considered: cosmetic-only repaint leaves information overload; new dashboard/framework rewrite risks behavior without helping existing tasks. Chosen judgement: targeted information hierarchy and progressive disclosure inside the existing app.
